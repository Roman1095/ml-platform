# ML Platform

Учебно-практическая платформа для запуска задач обучения моделей машинного обучения через API. API принимает задачу, сохраняет её состояние в PostgreSQL, а отдельный worker забирает задания из очереди, обучает модель и сохраняет артефакт.

> Сейчас проект ориентирован на локальный запуск через Docker Compose. Основной интерфейс для работы с API — Swagger UI. Веб-фронтенд в текущей структуре репозитория не предусмотрен.

## Возможности

- REST API на FastAPI с интерактивной документацией Swagger.
- Регистрация и вход пользователя, обновление токена и получение данных текущего пользователя.
- PostgreSQL для хранения пользователей, датасетов, задач обучения, логов, метрик и сведений об артефактах.
- Отдельный worker для выполнения задач обучения.
- Поддержка встроенных учебных датасетов: Iris, Wine, Breast Cancer и Digits.
- Обучение моделей scikit-learn; результат сохраняется как артефакт модели (текущий тестовый сценарий использует `joblib`).
- Сохранение файлов моделей, загруженных данных и логов в каталоги хоста, подключённые в контейнеры как volumes.
- Проверка жизненного цикла задачи, включая состояния выполнения и отмену задания.

## Архитектура

```text
Клиент / Swagger UI
        |
        v
FastAPI (порт хоста 18080)
        |
        +------> PostgreSQL (порт хоста 5432)
        |
        v
Очередь задач в PostgreSQL <------ Worker
                                      |
                                      +--> обучение модели
                                      +--> метрики и логи
                                      +--> файл артефакта в ./models
```

В проекте используются следующие сервисы Compose:

| Сервис | Назначение | Адрес / расположение |
|---|---|---|
| `api` | REST API и Swagger | `http://localhost:18080`, документация — `/docs` |
| `worker` | Выполнение задач обучения | Отдельный контейнер, без опубликованного HTTP-порта |
| `db` | PostgreSQL | `localhost:5432` с хоста; внутри Compose — `db:5432` |

## Требования

- Git
- Docker Engine или Docker Desktop
- Плагин Docker Compose v2 (`docker compose`)
- Свободные порты `18080` и `5432`

Python на хостовой системе для стандартного запуска не нужен: API и worker запускаются в Docker-контейнерах.

## Запуск с нуля

### 1. Клонировать репозиторий

```bash
git clone https://github.com/Roman1095/ml-platform.git
cd ml-platform
```

### 2. Создать файл `.env`

В корне проекта создайте `.env`. Пример для локального запуска:

```dotenv
POSTGRES_DB=ml_platform
POSTGRES_USER=ml_platform
POSTGRES_PASSWORD=change_this_local_password

DATABASE_URL=postgresql+asyncpg://ml_platform:change_this_local_password@db:5432/ml_platform
JWT_SECRET=replace_with_a_long_random_secret

ACCESS_TOKEN_EXPIRE_MINUTES=30
REFRESH_TOKEN_EXPIRE_DAYS=7
ARTIFACT_ROOT=/data/models
```

Важно:

- Значение `POSTGRES_PASSWORD` должно совпадать с паролем в `DATABASE_URL`.
- В `DATABASE_URL` имя хоста должно быть `db`, а не `localhost`: API подключается к PostgreSQL из другой контейнерной сети.
- Для `JWT_SECRET` используйте длинное случайное значение. Например, его можно сгенерировать командой `openssl rand -hex 32` и вставить в `.env`.
- Это пример локальной конфигурации. Если имена параметров в `backend/app/core/config.py` изменились в вашей ветке, сверяйтесь с этим файлом.
- Не публикуйте `.env` и не используйте показанные здесь демонстрационные значения пароля/секрета в production.

### 3. Создать локальные каталоги для данных

```bash
mkdir -p storage models logs
```

Compose монтирует эти каталоги в контейнеры:

- `./storage` — хранилище данных;
- `./models` — сохранённые модели и артефакты;
- `./logs` — файлы логов, если приложение их записывает.

### 4. Собрать образы и запустить сервисы

Из корня репозитория выполните:

```bash
docker compose up --build -d
```

Проверить состояние контейнеров:

```bash
docker compose ps
```

Ожидаются сервисы `ml_platform_db`, `ml_platform_api` и `ml_platform_worker` в рабочем состоянии.

### 5. Открыть Swagger UI

Перейдите в браузере по адресу:

**http://localhost:18080/docs**

Главная страница API доступна по адресу `http://localhost:18080/`, если для корневого пути настроен обработчик.

## Первый сценарий: проверить API и запустить обучение

1. Откройте Swagger: `http://localhost:18080/docs`.
2. Найдите эндпоинты авторизации и зарегистрируйте пользователя.
3. Выполните вход и получите access token.
4. Нажмите **Authorize** и укажите токен в формате `Bearer <access_token>`, если Swagger не подставляет префикс автоматически.
5. Получите список доступных встроенных датасетов. В текущей реализации предусмотрены Iris, Wine, Breast Cancer и Digits.
6. Создайте задачу обучения через эндпоинт задач (`/api/jobs`), выбрав датасет и параметры поддерживаемой модели.
7. Проверьте статус задачи, прогресс, логи и метрики через соответствующие эндпоинты API.
8. После завершения проверьте сведения об артефакте. Файлы модели сохраняются в каталоге `models/` на хостовой машине.

Названия и обязательные поля запросов лучше проверять непосредственно в Swagger: схемы запросов в документации формируются из текущего кода API и являются источником актуальных полей.

## Полезные команды Docker Compose

Посмотреть состояние сервисов:

```bash
docker compose ps
```

Посмотреть логи всех сервисов:

```bash
docker compose logs --tail=100
```

Следить за логами API и worker в реальном времени:

```bash
docker compose logs -f api worker
```

Посмотреть только логи PostgreSQL:

```bash
docker compose logs -f db
```

Перезапустить сервисы:

```bash
docker compose restart
```

Пересобрать образы и перезапустить сервисы после изменения Python-кода или зависимостей:

```bash
docker compose build --no-cache --pull
docker compose up -d
```

Остановить контейнеры:

```bash
docker compose down
```

`docker compose down` сохраняет именованный том `postgres_data`, поэтому данные PostgreSQL сохраняются при обычной остановке.

> **Осторожно:** `docker compose down -v` удаляет именованные volumes, в том числе данные PostgreSQL. Используйте эту команду только если намеренно хотите сбросить базу.

## Схема базы данных

В корне репозитория находится `schema.sql` с SQL-описанием схемы. В `docker-compose.yml` файл не подключён к стандартному каталогу инициализации PostgreSQL (`/docker-entrypoint-initdb.d`), поэтому не следует считать, что Docker автоматически исполняет его при первом старте. Инициализация таблиц должна соответствовать механизму, реализованному в текущем коде приложения. Если API сообщает об отсутствующих таблицах, проверьте логи и способ инициализации схемы перед ручным повторным применением SQL.

## Где искать код

```text
ml-platform/
├── backend/             # API, конфигурация, модели и worker
├── docker-compose.yml   # сервисы PostgreSQL, API и worker
├── schema.sql           # SQL-схема базы данных
├── storage/             # локальное хранилище данных (создаётся при запуске)
├── models/              # артефакты моделей (создаётся при запуске)
└── logs/                # локальные логи (создаётся при запуске)
```

## Устранение неполадок

### Swagger не открывается

```bash
docker compose ps
docker compose logs --tail=200 api
```

Убедитесь, что порт `18080` не занят другим приложением и контейнер API запущен.

### Worker не берёт задачи

```bash
docker compose logs --tail=200 worker
docker compose logs --tail=100 db
```

Проверьте, что PostgreSQL здоров, worker запущен и API создал задачу без ошибки. Для поиска причин используйте идентификатор задачи и сообщения из логов.

### Ошибка подключения к PostgreSQL

Проверьте совпадение `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и параметров `DATABASE_URL`. Из контейнеров Compose PostgreSQL доступен по адресу `db:5432`.

### Изменили `requirements.txt`, а ошибка импорта осталась

Пересоберите образ без кэша и запустите контейнеры снова:

```bash
docker compose build --no-cache --pull
docker compose up -d
```

### Нужно начать с чистой базой

Сначала остановите контейнеры, затем осознанно удалите volume базы:

```bash
docker compose down -v
docker compose up --build -d
```

Это удалит данные PostgreSQL. Перед выполнением сохраните нужные данные.

## Текущее состояние и дальнейшее развитие

Проект развивается поэтапно. Перед использованием в production необходимо отдельно проверить управление секретами, миграции и резервное копирование PostgreSQL, контроль доступа к артефактам, лимиты ресурсов worker, восстановление незавершённых задач после сбоя и мониторинг состояния worker-узлов. Не считайте наличие отдельного worker и Docker Compose само по себе гарантией production-ready эксплуатации.
